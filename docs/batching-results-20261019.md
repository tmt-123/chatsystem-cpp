# 有界微批实测摘要（2026-10-19）

实现见 [微批设计](bounded-message-batching.md)，项目来源见 [调研记录](performance-research.md)。本轮源码还未合入主线，不能将 ES 单层探针成绩当作完整 IM 性能。

## 条件

共享 Ubuntu 20.04 主机，双路 Xeon Silver 4310、48 逻辑 CPU、约 125.5 GiB 内存；7 服务和 5 中间件共用逻辑 CPU 0–3，负载端 CPU 4–7。256 B 单聊文本，同机 Docker bridge、无 TLS，MySQL SSD、ES 机械盘。MySQL flush_log_at_trx_commit=1、sync_binlog=1，ES translog=REQUEST，未降低持久化设置。

500 个发送用户各 1 条/秒，共 1000 WS，不是同时 500 个在途 HTTP 请求。账号和会话已预置，未混合群聊扇出、关键词检索和大文件。

## 对照

100/s、预热15秒/正式45秒，每轮正式4500条均HTTP/ACK成功，含预热6000条最终SQL/ES一致。

| 路径 | SQL采样速率 | ready采样 | 结束后核验等待 |
|---|---:|---|---:|
| 原版4workers/prefetch16，第1轮 | 56.48/s | 单调升至2477 | 46.43s |
| 保留单条，仅prefetch64 | 57.16/s | 单调升至2325 | 47.23s |
| ES Bulk、逐条SQL | 100.50/s | 四次均0 | 0.28s |
| ES Bulk、批SQL | 99.94/s | 四次均0 | 0.32s |
| 后续反向回测原版 | 60.82/s | 单调升至2312 | 38.24s |
| 后续新版匹配回测 | 100.44/s | 四次均0 | 0.36s |

只扩大prefetch没有解决存储积压。收益来自整个批写路径，包含请求/日志聚合；不是单独剥离所有因素后的纯ES API消融。SQL批事务并非本机达到500/s的必要条件：相同32/128参数的逐条SQL模式同样通过500/s单轮测试；不据此编造独立吞吐提升百分比。

## 最终确认

显式参数：workers4、prefetch128、batch_size32、wait10ms、sql_batch=true。

- 三轮各45秒，共67500条正式HTTP/ACK成功；每轮含预热30000条最终SQL/ES正确。合并HTTP P95 3.65ms、ACK P95 4.22ms。
- 500/s持续300秒，正式150000/150000 HTTP/ACK成功；含预热165000条，SQL唯一记录、ES文档的ID/会话/正文全部一致。
- 长测HTTP P95 3.89ms、P99 8.70ms，ACK P95 4.48ms；这些不是逐条持久化延迟。
- SQL采样499.99/s，ready采样峰709、末尾0；结束后1.38秒完成核验。ready不含最多128条未确认投递，不是全程零积压。
- 长测批回调16220次、投递165000次，平均批大小10.17；重试和拒绝计数均0。
- 后端平均CPU176.85%（100%=一个逻辑核）；工作集采样峰2132.62MiB。整机、容器内存配额和文件缓存不能换算成“4核2G机器支持500QPS”。

61项GTest、20项真实RabbitMQ回归通过；SQL trigger故障验证8条整批回滚、恢复后8SQL/ES一致；Message/ES暂停各50条恢复后无缺失，历史接口无需手工重启。20组链路数据共411230条接受消息最终内容审计一致；原始脚本失败日志保留，修正后以新场景重测。

数据随测试增长、主机非独占、采样有限，500/s是已验证负载而非最大容量。没有声称弱网/大文件/多实例全局顺序、publisher confirms或broker断电不丢消息。源代码、原始样本、构建/测试日志及部署条件保存在独立报告包，不把真实账号、令牌、私有配置、二进制或运行原始数据提交到仓库。
